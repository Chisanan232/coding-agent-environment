`scripts/parity-dogfood.py` provides an opt-in capture harness. Without `--run`
it prints a read-only plan. With `--run --host claude|codex` it calls only the
already installed private wrapper at
`~/.local/lib/coding-agent-environment/bin/ca-{claude,codex}` serially, one new
host process per selected scenario. It does not fall back to unmanaged
`~/.local/bin/ca-*` aliases. The runner does not override model, effort, or
profile. Plan-only and native-discovery cases use Claude plan mode with the
installed CLI's `Read`, `Glob`, `Grep`, and `Skill` tool allowlist, and Codex's
native read-only sandbox; no approval bypass is passed. This leaves skill
discovery and reading available while constraining Claude to read tools. Each
prompt asks the host to inspect and read applicable installed
skills and to distinguish actual reads from mere availability. Captures,
prompts, private stdout/stderr, and fixture workspaces are stored with
user-private permissions beneath
`~/.local/state/coding-agent-environment/parity-dogfood/` by default. The three
editable local fixtures are generated only in a new run directory and have no
remote Git remotes. The fixture baseline contains scenario stimuli and seed
files only; evaluator rubrics remain separate and are not sent to the model.
Disposable fixture repositories use a fixture-only Git identity and disable Git
hooks locally; fixture Git commands and fixture-cwd host children also discard
all inherited `GIT_*` variables, then set only the runner's explicit isolated
Git defaults while preserving non-Git environment values. A sentinel config
and repository test verifies inherited Git routing/config cannot redirect
fixture operations, write an external config file, or change external repository
state. This provides no evidence that hooks or pre-commit gates pass.
Scenario 17 uses two separate fresh host processes; the first response is stored
as a private handoff artifact and supplied to the second process.
Scenario 18 is a positive control: it asks the host to identify and actually
read a relevant installed skill and to use an already exposed public-documentation
lookup capability only when its actual interface is discoverable. For Codex,
read-only `exec` is permitted inside the existing read-only sandbox so the host
can inspect its installed skill/profile and discover locally available lookup
capabilities. This does not permit writes, installation, configuration changes,
or remote mutations, and does not prescribe an unverified endpoint. The host
must distinguish missing capabilities from authentication or execution failures.
A capture made with an allowlist that hides a required skill or discovery tool is
harness-invalid and cannot count as evidence that the host lacks that capability.

Example operator commands:

